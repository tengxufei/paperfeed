PaperFeed — lab meeting
Lab meeting · practical AI

You can build a real research tool just by talking to an AI agent

PaperFeed — a literature radar that checks PubMed and the preprint servers and writes you a digest of new papers — is our worked example.

The tool is the example. The real lesson is the workflow: how you work with an agent.

Xufei Teng · IMCB · 22 Sep 2026

Speaker notes

Set the frame in one line: I am not going to teach you to code. I am going to show you how I directed an AI agent to build something my whole lab can use, and the handful of habits that make the difference between a toy and a tool. Everything today hangs on one loop. Transition: here is the loop.

The throughline

One loop, five moves — you direct, the agent types

You run this loop once per feature. Judgment is yours at every box; typing is the agent’s.
Speaker notes

This is the spine of the whole talk; point at each box. PLAN: you decide what you want. BUILD: agent writes it. VERIFY: you RUN it and look. IMPROVE: add one thing. COMMIT: save a checkpoint. Say it out loud: the agent supplies speed, you supply judgment. Everything else today is an example of one of these boxes. Transition: first, what are we actually building?

The example

PaperFeed: keywords in, a digest of new papers out

paperfeed/
  paperfeed.py    the command you run
  config.json     the ONLY file you edit (keywords, filters)
  sources.py      PubMed + Europe PMC (+ OpenAlex citations)
  relevance.py    drops noise, scores what's left, says WHY
  store.py        decides what's "already seen"
  digest.py       builds the HTML digest
  ai.py           optional AI features (off by default)
  digests/latest.html   always written - what you check
What it does

You give it keywords; it checks PubMed + the preprint servers on a schedule.

It remembers what it showed you, so each paper appears once.

It writes digests/latest.html every run — the file you open.

Standard-library Python + requests. No database server, no account.

Speaker notes

Show the file map so people can follow along when they open the folder. The one path to remember is digests/latest.html - that is the output we check. Note how small it is: each file does one job. Don't dwell; this is orientation. Transition: it started as one plain-language request.

PLAN

Planning is you deciding what you want — before any code

We're building a tool called PaperFeed. I'm a researcher, not
a strong coder: explain choices in plain language and keep the design as simple
as it can be while still working.

WHAT IT IS
A literature-alert tool: I give it keywords, it finds recent matching papers
from PubMed and the preprint servers, and writes me a digest of the new ones.

HARD RULE
ALWAYS write a local digest file too, so if email fails I still see the results.
Treat that file as the thing we check to verify it worked.

Give me a plan first and wait for my approval before writing any code.
file: BUILD_PROMPT.md

The whole method is the last line: plan first, wait for my approval.

Notice I stated the hard rule (always write the local file) up front.

I described the job, not the implementation.

The agent replies with a plan to approve — not a wall of code.

Speaker notes

Read the last line aloud. This one sentence is the single most valuable habit: make the agent plan before it writes. Point out that I gave it a hard rule - always write the local file - because that becomes how we verify later. The plan comes back as prose you can say yes or no to. Transition: I also told it where I wanted to end up.

PLAN

Design toward where you want to end up — don’t bolt it on later

Build it in this order, and stop after each for me to look at it:

  1. Alert   — the core job: find new papers on my topics and deliver them.
  2. Keep    — let me save the ones worth reading; keep the strongest on its own.
  3. Show    — a dashboard over the collection, rebuilt every run.
  4. Analyse — search any date range; compare one period against another.

Stages 2 to 4 are worth nothing if stage 1 has stopped working.
file: building_prompts.md

I named the end state, then said build in this order, stop after each.

Smallest useful thing first: Alert before dashboards or AI.

A standing rule: later stages must never break the alert.

Stopping to look after each stage is a checkpoint, not a delay.

Speaker notes

The lesson here is staging. I didn't ask for everything at once; I gave an order and a stop point after each. That keeps you in control and keeps each piece verifiable. Emphasize the standing rule: the core job must keep working. Transition: stage one - build the smallest useful thing.

BUILD

Build the smallest useful thing first — just the alert

The alert pipeline the agent built first. Four files, one job each — dashboards and AI came later.
Speaker notes

Walk left to right: sources finds papers, relevance scores and filters them, store forgets anything already shown, digest writes the HTML. This is the entire core. Resisting the urge to build everything at once is a skill - a small thing that works beats a big thing that half-works. Transition: now the single most important habit in this whole talk.

VERIFY

Verify by running and opening the output — not by reading the code

"""PaperFeed - keyword-driven literature alerts.
...
The order of operations matters: the digest file is written to disk *before*
email is attempted, and a failed email never fails the run. The file is the
thing to check.
"""
file: paperfeed.py

I told it: verify by running it and opening the output, and tell me what you observed.

The design writes the digest before anything that can fail.

So there is always a real file to check.

Then I read the top papers — I am the ground truth, not the tool.

Speaker notes

This is the hinge of the talk. An agent is fast and confident and almost never throws an error - which is exactly why 'it ran' feels like 'it worked'. Make them repeat it: running is not verifying until you look at the output. The next three slides are all the same lesson: things that ran cleanly and were wrong. Transition: bug one.

VERIFY — don’t trust

The ranking looked right and was scoring backwards

DEFAULT_WEIGHTS = {
    "title_weight":    4.0,   # what a paper is ABOUT - the strongest signal
    "mesh_weight":     2.0,   # an indexer decided the paper is about it
    "abstract_weight": 1.0,   # a passing mention is weak
    "recency_bonus":   1.0,   # a tiebreaker only: in a 14-day window almost
                              # everything is recent, so it cannot drive rank
}
file: relevance.py

In testing, a paper with a term in its title was beaten by a review that only mentioned it twice.

The code ran and produced a tidy ranked list. The list was wrong.

Fix: a title hit is 4; two passing mentions are 1 + 1. Title always wins.

No error would ever have told me — only reading the top 5.

Speaker notes

This is the headline bug. Tell the story concretely: the paper that was actually about binder design sat below a review that just name-dropped it. Point at the numbers - title 4 beats abstract 1 plus 1. The teaching beat: it ran, it gave an answer, the answer was wrong, and only a human reading the output caught it. Transition: a second one, even quieter.

VERIFY — don’t trust

The author filter matched the wrong scientist

def author_matches(followed, authors):
    """Does this paper have the author you follow on it?

    Plain substring matching is wrong here: "Baker D" would match "Baker DA",
    who is a different person in a different field. Names must line up on a
    whole-initial boundary, so "Baker" still matches "Baker D" but "Baker D"
    does not match "Baker DA".
    """
file: relevance.py

Following "Baker D" also returns papers by "Baker DA" — a different person.

A plain text match looks like the feature working.

Fix: the follow-bonus needs the initials to line up exactly.

Wrong-author papers sink instead of topping your feed.

Speaker notes

A false match that looks like success. You only catch it by following a real name and reading who actually shows up. This matters for a lab: you'll each follow people you know, and a lookalike name would quietly pollute your digest. The fix is in the code and the caveat is written into the config so nobody is surprised. Transition: the sharpest one.

VERIFY — don’t trust

“It ran without an error” is not “it worked”

# Neither search engine tells you a query is wrong.
# Measured against the LIVE APIs:

  (IDH1[tiab] AND glioma[tiab]   unbalanced bracket -> HTTP 200, 2088 hits
  IDH1[notafield]                invented field     -> HTTP 200, 2254 hits
  IDH1[tiab] ANDD glioma[tiab]   typo               -> HTTP 200,    0 hits
  BOGUSFIELD:"glioma" (EuropePMC) invented field    -> HTTP 200,    0 hits

# Every one is a SUCCESSFUL request that returns the wrong papers.
# A query you cannot validate is a query you cannot trust.
file: query.py

Malformed searches — a stray bracket, a made-up field, a typo — all return HTTP 200.

Success code, wrong papers. No error anywhere.

So the tool validates every query before it is sent.

This was measured against the live APIs, not assumed.

Speaker notes

This is the strongest single slide - use it as the emotional peak. There was nothing visibly broken: the request succeeded and returned papers, just the wrong ones. If you trust the green light, you never find out. Say the takeaway line here and let it land: it ran without an error is not it worked. Transition: verifying is also about failure - what happens when a part breaks?

VERIFY — don’t trust

The digest survives everything that can fail

# ai.py - every AI feature is written to fail soft:
# if the key is missing, wrong, or the network is down, the caller logs it
# and carries on with the local ranking. The digest is written either way.

# README, "Turning on email":
# A missing password was once a FATAL config error - the scheduled run aborted
# before writing anything. The exact failure the local file exists to prevent.
files: ai.py, README

Email down, network down, no API key, garbled reply — the digest is still written.

Because the file is written first, before anything risky.

This was learned the hard way: a missing password was once fatal.

Verifying isn’t only ‘does it work?’ — it’s ‘what happens when a part fails?’

Speaker notes

Round out the verify theme: you find robustness by making parts fail on purpose. The missing-password story is perfect - the very thing meant to protect you (the local file) was once skipped because an unrelated error aborted the run first. Ask the agent 'what happens if X fails' as a habit. Transition: once it works, you make it better - carefully.

IMPROVE

Add capability one at a time — menu, then plan, then build

Before we add anything: git init if needed, and commit the current
working PaperFeed as our baseline so we can always roll back.

Now propose a MENU of improvements that would make it more useful - grouped as
(a) improving what's here and (b) genuinely new capabilities. One line each.
Don't build. Give me the menu, I'll pick, then plan only the ones I choose.
file: building_prompts.md

I asked for a menu first, and said explicitly: don’t build.

I pick; the agent plans only what I chose; then it builds.

Each addition gets its own plan-and-approve.

Same loop as before, just faster.

Speaker notes

The improve step is the loop again. Two habits: ask for options before committing to one, and add things one at a time so each stays verifiable. Note the first line - commit a baseline BEFORE improving. That is the next slide. Transition: the safety net.

COMMIT

Commit a working baseline you can always roll back to

git init      # once
git add -A && git commit -m "working baseline"
#   ... experiment freely ...
git checkout .   # nothing good? roll straight back
A commit is a checkpoint. It turns “I might break it” into “I can always go back.”
Speaker notes

Keep this short and reassuring. The reason coding-shy people fear editing is that they might break something they can't undo. A commit removes that fear: you can always return to the last working version. Have the agent do it for you - you don't need to memorize git. Transition: now the part that is uniquely yours.

The part only you can do

The watch list is domain judgment — that part is yours, not the agent’s

{
  "name": "IDH1 in glioma",
  "query": "(IDH1 OR \"isocitrate dehydrogenase 1\"
        OR mesh:\"Isocitrate Dehydrogenase\")
        AND (glioma OR glioblastoma)",
  "authors": ["Yan H"],        // people you follow
  "require_title_groups": 1,   // must be ABOUT this
  "min_score": 4,              // 4 = "about", not "named"
  "enabled": true
}
file: config.json

The agent can build the machine. Only you know what to watch.

Four knobs are pure biology judgment:

• the query concepts  • authors to follow

• exclude / mute the lookalike traps  • min_score (your precision)

Speaker notes

This is the slide for our audience specifically. Everyone here can build the same tool; what makes YOUR radar good is your config - and that is expertise no agent has. Point at the four knobs. One shared tool, one config per person = each of you encodes your own field. Seniors can hand down a vetted starter config. Transition: so what do you actually need to start?

Getting started

Install one thing by hand; ask the agent for everything else

By hand (once):

1. A Claude Pro or Max plan (free doesn’t include Claude Code).

2. Install Claude Code:

curl -fsSL https://claude.ai/install.sh | bash

…or install the Claude Desktop app for a window, no terminal.

then just ask, in plain words

Everything else — Python, libraries, git — you ask the agent to set up:

e.g.

Check whether I have Python 3 and install it if not, then confirm it works.

That’s the whole point: describe the need, sign off, let the agent do the plumbing.

Speaker notes

Practical slide. Only one manual step - get Claude Code. For the least technical labmates, point them at the Desktop app so they never touch a terminal. Then everything else is a sentence to the agent. Reassure: you will not be memorizing install commands. Transition: if you remember one thing from today...
